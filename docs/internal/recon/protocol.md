# Gemini Protocol Specification: State of the Spec (Recon for Unseen Servant)

## Summary (researched 2026-08-09)

As of 2026-08-09, the authoritative Gemini specifications are two documents published at geminiprotocol.net, both at **version 0.24.1, released 2024-08-28**: the "Gemini network protocol specification" and the "Gemini hypertext format, aka 'gemtext', specification". Both are public domain (CC0 1.0). The version scheme is 0.YY.Q (two-digit year, zero-indexed quarter), adopted 2024-03-31 when both specs jumped to 0.24.0; 0.24.1 followed in Q3 2024. **No spec release has occurred since 2024-08-28**: the project news feed (checked 2026-08-09) shows no spec-related entries after 2024-10-24 ("Some more GitLab issues closed"), only site-migration and anniversary posts through 2026-06-20. The spec is therefore effectively frozen in practice, with a small set of maintainer-accepted changes queued for a hypothetical 0.24.2 that has not shipped in nearly two years. The historical spec-development repos at gitlab.com/gemini-specification (projects: `protocol`, `gemini-text`; no registry project exists in the group) have had no repository commits since 2021-11, the canonical text moved to geminiprotocol.net when Solderpunk resumed maintenance, but their issue trackers remain the record of open debates (protocol: 17 open issues, last activity 2025-04-17; gemini-text: 11 open issues, last activity 2025-12-08). Issue descriptions and metadata were retrieved via the GitLab REST API on 2026-08-09; **issue comment threads returned 401 Unauthorized via the API**, so characterizations of debates below rest on issue descriptions, comment counts, update dates, and the maintainer's dated news posts, not on full comment text. Neither the `gemini` URI scheme nor the `text/gemini` media type is IANA-registered (verified against the IANA uri-schemes and media-types registries on 2026-08-09); registration issues (protocol #6 and #16, gemini-text #11) remain open.

The practical upshot for a new server: implement exactly the 0.24.1 protocol spec, strictly. It is stable, precise (full ABNF for requests and responses), and the community treats it as final. The contested areas are almost entirely client-side concerns (TOFU details, fragment semantics, IRI display); the few server-relevant ambiguities are enumerated below with recommended strict behavior.

## Stable (rely on it)

Everything in this section is normative text in the v0.24.1 specs (published 2024-08-28, unchanged as of 2026-08-09) unless otherwise noted.

### Transport and addressing

- Gemini runs over TCP, default port 1965, with TLS mandatory for every transaction. One request, one response, then the server closes the connection. There is no keep-alive, no pipelining, no compression, no chunking, and no content or transfer encoding; the body is raw bytes and the end of the body is signaled by connection close.
- Addressing uses URIs per RFC 3986 (STD 66) with scheme `gemini`. The userinfo component MUST NOT be used and "a server MUST reject a request with a userinfo portion." An empty path and a path of "/" are equivalent and "servers MUST support both without sending a redirection." The port defaults to 1965. Use of an IP address in the authority SHOULD NOT be used (but is not forbidden).
- The spec is URI-based, not IRI-based. Requests are ASCII-percent-encoded URIs; internationalized hostnames must be punycoded by the client before request and resolution (see Contested: protocol issue #1).

### Requests

- A request is `absolute-URI CRLF`: nothing else. No headers, no version, no method. CRLF is CR (13) LF (10); the ABNF references STD 68 CRLF, so a bare LF terminator is not a conforming request (see Contested for lenience debate).
- "When making a request, the URI MUST NOT exceed 1024 bytes, and a server MUST reject requests where the URI exceeds this limit." Note carefully: the 1024-byte limit is on the **URI itself, in bytes, excluding the trailing CRLF** (so the maximum conforming request is 1026 bytes on the wire). This wording is from v0.24.1; the older speculative spec (v0.16.1, 2022-01-30) phrased it as a limit on the URL as well.
- "Clients MUST NOT send a fragment as part of the request, and a server MUST reject such requests as well."
- Clients SHOULD add a trailing '/' for an empty path, "but a server MUST be able to deal with an empty path."
- Status 59 ("bad request") is the designated response when "the server was unable to parse the client's request, presumably due to a malformed request, or the request violated the constraints listed in the Request section." So oversize URI, userinfo present, fragment present, non-absolute URI, and unparseable garbage all map to 59.

### Responses

- Response header: two-digit status code, then (depending on class) additional information, then CRLF. Full ABNF in the spec: `input = "1" DIGIT SP prompt CRLF`; `success = "2" DIGIT SP mimetype CRLF body`; `redirect = "3" DIGIT SP URI-reference CRLF`; `tempfail = "4" DIGIT [SP errormsg] CRLF`; `permfail = "5" DIGIT [SP errormsg] CRLF`; `auth = "6" DIGIT [SP errormsg] CRLF`.
- Consequences of that ABNF, all stable since 0.24.0 (2024-03-31, "Closing the spec gap" changes announced 2024-02-28): META is **mandatory** for 1x (prompt), 2x (MIME type), and 3x (redirect target) responses: the old "default to text/gemini on empty META" behavior was removed in 0.24.0 ("the previous optional default no longer applies"). META (error message) is **optional** for 4x, 5x, and 6x, and when omitted the SP separator is omitted too (the spec's own example is `"50" CRLF`).
- "Response headers MUST be UTF-8 encoded text and MUST NOT begin with the Byte Order Mark U+FEFF" (added in 0.24.1, 2024-08-28, closing protocol issue #36). Prompt and errormsg allow SP plus Unicode VCHAR (the ABNF extends VCHAR to non-control UTF-8, explicitly excluding the C1 control range).
- "Upon sending the complete response (which may include content), the server closes the connection and MUST use the TLS close_notify mechanism to inform the client that no more data will be sent." Both sides SHOULD handle a missing close_notify (a truncation attack indicator for clients; the server MAY log such cases on its own inbound connections).
- Status codes range 10-69; "Servers MUST NOT send status codes that are not defined." Clients MUST reject codes outside 10-69 and SHOULD treat undefined codes within range per their first digit. The complete list of defined codes in v0.24.1: 10 (input), 11 (sensitive input), 20 (success, the only 2x code), 30 (temporary redirect), 31 (permanent redirect), 40 (temporary failure), 41 (server unavailable), 42 (CGI error), 43 (proxy error), 44 (slow down), 50 (permanent failure), 51 (not found), 52 (gone), 53 (proxy request refused), 59 (bad request), 60 (client certificate required), 61 (certificate not authorized), 62 (certificate not valid). A server emitting anything else (e.g., 61/62 variants like 63, or 21) is non-conforming.
- Status 44 semantics changed in 0.24.0 (2024-03-31): the META is now an optional human-readable message, **not** a numeric wait-time in seconds as in the old v0.16.1 spec. The client "SHOULD use an exponential back off, where subsequent delays between requests are doubled until this status no longer returned."
- Input (1x): client re-requests the same URI with the input as the query, spaces encoded as %20; multi-line input linebreaks SHOULD be sent as %0A, and "servers SHOULD recognise both '%0A' and '%0D%0A' as linebreaks" (added 0.24.0). If the URI already has a query string, the client MUST replace it with the new input (clarified 0.24.1, closing protocol issue #19).
- Redirects (3x): META is an absolute or relative URI-reference; the spec notes an empty URI-reference "is not intended to be valid" for redirection. "If a server sends a redirection in response to a request with a query string, the client MUST NOT apply the query string to the new location": a server that needs the query preserved MAY bake it into the redirect target. Servers SHOULD NOT include fragments in redirects. "Client MUST limit the number of redirections they follow to 5 redirections" (limit added in 0.24.0, closing protocol issue #4; before that no numeric limit was normative).

### TLS

- "Servers and clients MUST support TLS 1.2 or higher." The spec text (unchanged since 2021 on this point) explains TLS 1.2 was kept only for library availability, and warns that TLS 1.2 sends SNI and client certificates in the clear; clients SHOULD warn users before sending a client certificate over TLS 1.2. Nothing forbids a server from requiring TLS 1.3 for its own policy, and the open debate (protocol issue #12) pushes in that direction.
- "Client and server implementations MUST support TLS SNI," clients MUST send SNI when the authority is a hostname, and (clarified in 0.24.1, closing issue #33) when the authority is an IP address clients SHOULD omit SNI entirely rather than send an empty value.
- Server certificate validation is deliberately not dictated: clients "are strongly RECOMMENDED" to use TOFU certificate pinning keyed on hostname+port (host+port scoping formalized in 0.24.0), which accepts self-signed certificates. Server-side consequence: self-signed certificates are first-class and CA-signed certificates are equally acceptable; the fingerprint is what clients pin, so certificate rotation is a user-visible event in TOFU clients and long-lived keys (or key-preserving renewal) are kind to them. The choice of CA-based versus self-signed certs is delegated to the (non-normative) best-practices document.

### Client certificates (protocol level)

- The 6x class means: resource requires a client certificate (60), or the presented one is not authorized for this resource (61), or is invalid in itself: expired, not yet valid, bad signature, X.509 violation (62). Servers SHOULD include an explanatory message in META.
- Certificate scope: host + port + the request path and everything below it. "A server MAY require a different certificate for a different path on the same host and port. A server SHOULD allow the same certificate to be used for any content along the given path." Clients MUST NOT auto-generate certificates without user involvement and MUST NOT reuse a certificate outside its scope unless the user directs it. A 2024-10-24 proposal to narrow scope to hostname-only (protocol issue #18) was **rejected**, preserving path-scoped multi-app hosting under one hostname.
- The protocol attaches no meaning to the certificate's issuer chain; self-signed, ephemeral client certificates are the norm and serve as session/identity tokens. Validity-period checking is the server's job (62). TOFU-style pinning of a client cert's public key against an application account is an application-layer pattern, not a protocol mandate.

### MIME and charset handling

- The 20 META is a MIME type per RFC 2045: `type "/" subtype *(";" parameter)`. Note the ABNF has no leading-whitespace allowance beyond the single SP after the status digit-pair.
- "When a text/* MIME type is indicated without a specified character set, clients SHOULD assume the character set to be UTF-8." Clients MUST support text/gemini in UTF-8 and text/plain in US-ASCII or UTF-8; other charsets are optional. Clients MUST ignore MIME parameters they do not understand.
- text/gemini defines one extra parameter, `lang`, holding BCP 47 tags (comma-separated lists MUST be quoted per RFC 2045 quoting rules, e.g. `text/gemini; lang="en,fr"`); it is optional, has no default, and parameters other than `charset` and `lang` are undefined (clients MUST ignore them).
- Canonical-form rule for text: Gemini permits bare LF instead of CRLF as the line break "when it is done consistently for an entire response body," but never bare CR. "Gemini clients MUST accept CRLF and bare LF as being representative of a line break in text media." So a server may serve LF-terminated files as-is.
- Text bodies in any Unicode encoding SHOULD NOT begin with a BOM; encoding belongs in the `charset` parameter. Clients SHOULD ignore a leading BOM in text/gemini when parsing (added 0.24.1).

### Gemtext (v0.24.1)

- Six line types, determined by at most the first three characters of the line, parsed in a single pass with exactly one bit of parser state (normal vs. pre-formatted mode; the parser MUST start in normal mode; state at EOF is meaningless).
- Core types every renderer MUST handle: text lines, link lines (`=>[<whitespace>]<URL>[<whitespace><NAME>]`, where whitespace is one or more spaces or tabs; URLs MUST percent-encode reserved characters and spaces per RFC 3986; the link target is a URI-reference, may be relative), and preformat toggle lines (first three characters exactly ```` ``` ```` with no leading whitespace; text after the opening toggle MAY be treated as alt text; text after a closing toggle MUST be ignored; toggle lines are not rendered).
- Optional types software MAY handle, and MUST otherwise render as plain text lines: headings (`#`, `##`, `###` plus optional whitespace then text: exactly three levels), list items (`* `: asterisk **plus mandatory space**, per the ABNF `list-item = "*" SP text-line`), and quote lines (`>` prefix, no space required, per `quote-line = ">" text-line`).
- Note the prefix asymmetry, which is normative and not a typo: list items require the space after `*`; headings take optional whitespace after the `#`s; quotes require nothing after `>`. A proposal to require a space after every marker (gemini-text issue #10) was never adopted.
- Empty lines are ordinary text lines, rendered as vertical space, never collapsed. Long text lines SHOULD be wrapped by clients; consecutive short lines MUST NOT be joined. Clients MUST NOT auto-fetch link targets during rendering. Tabs are permitted alongside spaces in link-line and text-line whitespace (0.24.1 change), and non-ASCII characters are allowed in text lines (0.24.1 ABNF fix). A gemtext document is `1*gemtext-line` (at least one line, an 0.24.1 ABNF fix closing gemini-text issue #14/#6 territory).

### Companion specs (non-core, stable conventions)

- robots.txt for Gemini (geminiprotocol.net/docs/companion/robots.gmi): servers wanting crawler control serve `/robots.txt` as text/plain with a reduced robots-exclusion syntax and virtual user-agents (archiver, indexer, researcher, webproxy). A Cloudron-deployed public server should support serving this file.
- Subscription convention (geminiprotocol.net/docs/companion/subscription.gmi): clients may poll a gemtext page and interpret heading + `=> URL YYYY-MM-DD - title` link lines as a feed. Purely a content convention; no server code needed beyond serving pages.

## Contested (open debate: implement conservatively)

All issue metadata below was read from the GitLab API on 2026-08-09. Comment bodies were not readable anonymously (401), so debate summaries derive from issue descriptions, comment counts, activity dates, and the maintainer's news posts.

- **URI vs. IRI / internationalization (protocol issue #1, opened 2021-03-01, 66 comments, last activity 2021-04-07; the group's most-discussed issue).** Proposal: switch requests to IRIs (RFC 3987), with servers/clients required to handle UTF-8 hostnames and punycode conversion for DNS. The maintainer explicitly deferred all IRI work out of the 0.24.x cycle (news post 2024-03-31: 0.24.1 would target "non-IRI-related improvements," internationalization "deferred to later development phases"). Related: gemini-text issue #8 (IRIs in link lines, 2021, 9 comments). Conservative stance: accept and emit only RFC 3986 URIs; treat raw non-ASCII bytes in a request as malformed (59); expect clients to have punycoded hostnames and percent-encoded paths. Note the 2024-10-24 news post's rationale for allowing URIs (not just URLs) in gemtext link lines shows the maintainer is sympathetic to eventual internationalization: do not build in assumptions that make IRI support impossible later.
- **Trailing CRLF strictness on requests (implied by the ABNF; perennial implementers' argument, surfaced in e.g. the 2024-07-30 "Moving slowly and breaking things" news cycle).** The ABNF requires CRLF; the spec never authorizes accepting a bare-LF request. Real-world clients occasionally send bare LF. A strict server rejects (59) any request line not terminated by exactly CRLF; that is the defensible reading, and rejection also closes request-smuggling-adjacent ambiguity. There is no open issue proposing to relax this on the protocol tracker as of 2026-08-09.
- **Status 11 sensitive input (protocol issue #17, closed 2024-10-24 as "rejected removal; clarification planned").** Status 11 survives but is widely considered a footgun (the input still travels in the URL query; it is protected by TLS in transit but appears in logs and history). The maintainer's stated position (news 2024-10-24) is that 11 is meant to be combined with client certificates, and that a security discussion will be added in the next spec update. Server guidance: never design applications that accept passwords via 11 without a client-certificate binding; treat query strings as loggable-sensitive and consider redacting queries from logs by default.
- **Client certificates over TLS 1.2 (protocol issue #12, opened 2021-03-03, 19 comments, last activity 2025-01-10).** Proposal: permit client certificates only over TLS 1.3+, because TLS 1.2 exposes them in cleartext. Not adopted; the spec merely has clients warn. Still actively referenced. Conservative server stance: prefer TLS 1.3; if you accept TLS 1.2 at all, consider refusing to request client certificates on 1.2 connections, or simply require TLS 1.3 outright (nothing in the spec forbids a stricter server).
- **TLS server certificate trust details (protocol issue #5, opened 2021-03-01, 28 comments, last activity 2024-10-27).** What exactly a TOFU client should pin (whole cert, fingerprint, public key) is unsettled; formal alternative validation schemes "may evolve out of solidifying practices" (spec text). Server consequence: assume clients pin the certificate fingerprint; avoid gratuitous certificate/key churn and document rotation for users.
- **Fragments and redirection (protocol issue #8, opened 2021-03-01, 12 comments, last activity 2025-01-11) and fragment semantics in gemtext (gemini-text issue #3, opened 2021-03-01, 58 comments, last activity 2024-02-04).** Fragments have no defined meaning in gemtext, and redirect-fragment interaction is only half-specified (0.24.1 says servers SHOULD NOT put fragments in redirects, client picks which fragment wins otherwise). Server stance: never emit fragments in redirect METAs; reject requests containing fragments (that part is settled and mandatory).
- **META clarifications and whitespace edges (protocol issue #3, opened 2021-03-01, 12 comments, last updated 2022-05-03).** The mandatory-META ABNF that came out of this issue landed in 0.24.0, but the issue remains open, and residual edge questions (exact whitespace between status and META, treatment of a status line with trailing spaces) linger. Strict emission: exactly one SP, no trailing whitespace before CRLF, omit `SP` entirely when omitting an optional errormsg.
- **TLS session resumption (protocol issue #23, opened 2021-04-05, 7 comments, last activity 2023-10-20)** and **client-fingerprinting concerns (issues #38/#39, 2021, activity through 2024-10-27)**: whether servers should support (or clients use) session tickets, given tracking potential. Unsettled. Privacy-conservative server: disable TLS session tickets/resumption, or at minimum make it configurable and off by default. Related privacy items still open: forbidding OCSP fetches (issue #13) and CSRF-style concerns for client-cert-authenticated apps (issue #37, last activity 2025-01-10).
- **New status codes and richer input (protocol issue #45 "Better input support," opened 2022-11-25, last activity 2025-04-17: the tracker's most recently active protocol thread; issue #48 "new success status code," 2025-01-21; issue #46 "Support Image," 2024-11-15).** None accepted. Servers MUST NOT emit undefined codes, so these are watch-only.
- **Gemtext edge cases still open (gemini-text tracker):** escaping ``` inside preformatted blocks (issue #17, opened 2022-12-14, last activity 2024-02-17, currently impossible; variable-length fence proposal undecided), limits on `data:` URIs in link lines (issue #16, 2022-02-21: maintainer voiced support 2024-10-24 for adding length limits "in the next update"), which whitespace characters count (issue #15, 2021-12-23), screen-reader treatment of preformatted alt text (issue #12, 2021), and decorative/IRC formatting or math extensions (issues #19, 2024-10-14; #20, 2025-12-07, the tracker's newest thread). None of these change server behavior; they affect authored content and clients.
- **Port and scheme registration (protocol issues #16 and #6, 2021, both open).** Verified 2026-08-09: `gemini` is absent from the IANA URI-scheme registry and `text/gemini` from the media-types registry (gemini-text issue #11 also open). Port 1965 is likewise unregistered. This has no implementation impact but matters for packaging documentation honesty.

## Forthcoming (accepted but not in the published spec)

These are maintainer-accepted or maintainer-endorsed changes announced in dated news posts but never published, because no release has followed 0.24.1 (2024-08-28). Treat them as the likely content of an eventual 0.24.2/0.25.x.

- A security-considerations discussion for status 11 (sensitive input), clarifying that it should be used together with client certificates (announced 2024-10-24 when rejecting removal of code 11).
- Length limits on `data:` URIs in gemtext link lines, to curb abuse after link-line targets were confirmed as URIs generally (maintainer support stated 2024-10-24; gemini-text issue #16).
- Consistent whitespace requirements across all gemtext line types, and a possible mandate that gemtext documents be UTF-8 encoded (both flagged 2024-08-28 as decisions "before version 0.24.2").
- The broader trajectory stated 2024-03-31: continue quarterly-numbered releases toward finalization, with IRI/internationalization as the only large open workstream, deferred indefinitely. Given the release drought since, plan for 0.24.1 semantics as the long-term reality.

## Implementation guidance for Unseen Servant

A strict, security-first server should resolve every ambiguity toward rejection, minimalism, and TLS 1.3:

1. **Request parsing.** Read at most 1026 bytes for the request line (1024-byte URI + CRLF). If no CRLF appears within that window, respond `59` and close. Require the terminator to be exactly CRLF; reject bare LF, bare CR, or embedded control bytes with `59`. Parse the URI with a strict RFC 3986 parser; require scheme `gemini` (or reject with `53` if it is a well-formed URI for a foreign scheme/host, since we are not a proxy), reject userinfo (`59`), reject fragments (`59`), reject non-ASCII bytes (`59`). Treat empty path and "/" as the same resource without redirecting. Compare hostnames case-insensitively; expect punycode, never IDN-decode server-side. Verify the request's authority matches a hostname and port this server is configured to serve; otherwise `53` (proxy request refused).
2. **Response emission.** Always emit `XX META CRLF` with exactly one SP for 1x/2x/3x; for 4x/5x/6x either `XX CRLF` or `XX SP message CRLF`. Never send an empty META on 20: a MIME type is mandatory; configure a real default per file extension and fall back to `application/octet-stream` for unknown binaries, adding `; charset=utf-8` explicitly for text/gemini even though clients should assume it. Keep headers UTF-8 with no BOM and no control characters. Never emit undefined status codes. After the last body byte, perform a proper TLS close_notify before TCP close: this is a hard MUST and TOFU clients treat missing close_notify as truncation.
3. **Redirects.** Emit only 30/31 with a non-empty absolute or relative URI-reference in META, never a fragment, and never rely on the client re-applying a query string: if the query matters, encode it in the target. Cap any internally-generated redirect chains (e.g., directory-slash normalization) well below the client-side limit of 5; ideally a single hop.
4. **TLS.** Default to TLS 1.3-only; offer TLS 1.2 as an explicit opt-in for the operator, and if 1.2 is enabled, prefer not to request client certificates on 1.2 connections (issue #12's concern). Support SNI-based virtual hosting; if a ClientHello has no SNI, serve the configured default host or refuse, but never crash. Accept self-signed server certificates as the deployment norm (generate/renew keeping the key stable if possible, since TOFU clients pin fingerprints); Cloudron will typically supply Let us Encrypt certs, which are equally valid. Disable TLS session tickets/resumption by default (fingerprinting concern, issues #23/#39). Do not fetch OCSP or emit stapling requirements (issue #13 direction).
5. **Client certificates.** Request them only for configured path scopes. Enforce scope as host + port + path-prefix per the spec's example table. Accept self-signed and even expired-CA-chain-free certs at the TLS layer, then apply protocol semantics yourself: `60` when a scope requires a cert and none was presented; `62` for not-yet-valid/expired/malformed certificates; `61` for valid certificates that are not on the authorized list for that scope. Always include a human-readable META with 6x. Identify certificates by public-key or certificate fingerprint (SHA-256) for authorization lists.
6. **Status 44 and abuse control.** Use `44` (optional human message, no numeric META: the wait-seconds semantics died with v0.16.1) for rate limiting, and pair it with real server-side throttling since clients may ignore it.
7. **Content service.** Serve files as-is: bare-LF text files are legal on the wire, so no CRLF conversion is needed. Strip or avoid BOMs in generated text. For text/gemini, follow the 0.24.1 gemtext ABNF when generating content (directory listings, error pages): `* ` with the space for lists, ```` ``` ```` fences never nested (there is no escape mechanism: do not generate content requiring one), at most three heading levels, percent-encoded URLs in link lines. Serve `/robots.txt` as text/plain per the companion spec.
8. **Logging and privacy.** Treat query strings as sensitive (status 10/11 input lands there); redact them from logs by default. Log missing client close_notify at debug level only (spec: server MAY log).
9. **Ambiguity policy.** Where the spec is silent (e.g., request bytes arriving after the CRLF: the client has nothing more to say in this protocol; or TLS renegotiation), close the connection. A closed issue (#40, 2021-11-07) addressed extra client data; the resolution in practice is that servers need not read beyond the first CRLF.
10. **Watch list for future spec work.** Nothing accepted-but-unpublished (status-11 security text, data:-URI limits, gemtext whitespace/UTF-8 mandates) requires server code changes; all can be absorbed later without breaking anything if the above strict behavior is implemented now. The only development that could force real rework is IRI adoption, which is deferred indefinitely.
