# ADR 0003: Certificate lifecycle — Agate's model, deployment-aware, never silently regenerated

- Status: Accepted (pending director review)
- Date: 2026-08-09
- Evidence: docs/recon/prior-art.md §1, docs/recon/cloudron-fit.md §2–3, docs/recon/protocol.md (TLS/TOFU sections)

## Context

Under TOFU, the keypair *is* the capsule's identity: clients pin the
certificate fingerprint, and rotation is a user-visible trust event.
Agate's lifecycle is best in class (auto-generation, effectively-never
expiry, per-hostname layout) and its issue tracker shows certificate
ergonomics are what users actually need. Cloudron recon adds three
facts: `/app/data` is the only surviving location (with a precise
survival table in cloudron-fit.md §3); clone/move operations carry the
keypair to a **new hostname**; and the `tls` addon exposes Cloudron's
Let's Encrypt cert at `/etc/certs/tls_{cert,key}.pem` — so CA-signed
is possible, but LE's ~60–90-day rotation breaks TOFU pinning, which
is why it must not be the default.

## Decision

- **Auto-generate on first run**: ECDSA P-256, self-signed, notAfter
  **4096-01-01** (Agate's convention — expiry churn adds nothing under
  TOFU), CN/SAN = configured hostname, key file mode 0600.
- **Per-hostname subdirectories** under the certs directory
  (`<certs>/<hostname>/cert.pem` + `key.pem`), most-specific-match
  wins, SNI selects at handshake. The certs directory lives under the
  state root: `/app/data/certs` on Cloudron, `${state_dir}/certs`
  standalone (ADR 0008).
- **PEM is the on-disk format**; DER accepted on read for
  compatibility with Agate migrants. Operators may drop their own
  cert/key into the same slots; user-supplied material is never
  touched.
- **Never silently regenerate.** Generation happens only when a
  hostname's slot is empty. A corrupt or unreadable keypair is a
  startup error with a loud, actionable message — not a regeneration.
- **Hostname-change detection**: usv records the hostnames it has
  minted certs for. When the configured hostname has no cert but
  another hostname's autogenerated cert exists (the Cloudron
  clone/move signature), usv mints a fresh keypair for the new
  hostname, keeps the old one on disk untouched, and logs exactly what
  happened and why. It never reuses an old hostname's key for a new
  hostname and never deletes anything.
- **SIGHUP reloads certificates** without dropping listeners
  (ADR 0002), so operators can rotate material with zero downtime.
- **CA-signed opt-in**: a config flag points usv at externally managed
  cert/key paths (on Cloudron: the `tls` addon's `/etc/certs/…`). The
  documentation states plainly that CA rotation will trip TOFU pinning
  warnings in clients; self-signed remains the default and the
  recommendation.
- **The TOFU survival story is documented in UPGRADING.md**: what
  survives restart, update, restore, clone, move, migration; that
  uninstall destroys identity unless a backup is retained; and how to
  back up `certs/` by hand in standalone deployments.

## Consequences

- Identity survives everything the platform preserves, and every
  identity-affecting event leaves a log line and an untouched old
  keypair — nothing is ever lost silently.
- Multi-hostname capsules (Cloudron `multiDomain`, standalone vhosts)
  fall out of the per-hostname layout for free.
- We inherit Agate's one sharp edge knowingly: far-future expiry makes
  strict-CA clients warn once. That is the TOFU trade, and it is
  documented rather than "fixed".
